# 默认简单，按需求增加状态

本技能服务于从“开始上传/停止读取”到多通道采集仪的连续需求范围。目标是让简单功能容易开发，让后续优化有明确的归属和边界。不是让每个项目都采用同一个框架。

## 1. 默认从五个问题开始

对当前功能先回答：

1. 需要记住什么，才能决定下一个输入怎么处理？
2. 这份信息由谁修改？
3. 同一个命令重复到达时怎么办？
4. 如果需要等，等多久，等不到怎么办？
5. 调用方如何知道完成、失败或结果暂时不确定？

答案可以放在一个小结构、一个处理函数和一张短表中。没有跨事件等待，就不强制持久化一个执行阶段；没有多个未决操作，就不先创建通用请求调度器；没有恢复承诺，就不自动增加重试/回滚引擎。

这些判断不能省略，但实现形式不固定。由同一上下文串行处理且耗时有界的小驱动调用，可以直接由命令处理逻辑完成；不为满足“分层”额外创建 Task、队列和 manager。调用不能破坏其他实时职责或占用需要处理其完成的事件循环。

## 2. 什么才需要成为状态

判断依据是：**后续行为是否依赖这段必须保留的历史**。需要状态时如实表达；能用现有状态和输入计算的结果不另存可写副本。

| 新需求 | 首选表示 | 何时才需要额外状态 |
|---|---|---|
| 上传速率、通道数、包大小 | 参数/配置 | 应用参数需要跨事件等待，才加局部迁移阶段 |
| 重试最多 2 次 | 当前操作的剩余次数 | 若两次重试的行为不同，才区分不同阶段 |
| 是否 busy | 从活动操作或状态推导 | 多个独立活动存在时定义聚合规则，不随处写 busy |
| 错误原因 | 结果码、诊断字段 | 错误改变后续允许操作时，才需要故障/降级模式 |
| 等 FPGA 停止确认 | 局部 STOPPING + deadline | 等待确实跨越处理轮次时需要，不能藏在无限循环里 |
| USB/BLE 链路连接 | 通信模块事实 | 不生成 MEASURE_USB、MEASURE_BLE 等组合模式 |
| 通道 1～8 参与本次采集 | channel mask 或配置数组 | 只有通道可独立启停/恢复时，才有每通道运行状态 |
| 同时处理两条变更命令 | 先明确是否必要 | 必须并发时，才增加请求表、冲突和资源仲裁 |

计数器、位图和局部上下文也是系统状态，改掉 enum 名称并没有消除组合空间。它们的价值是让变化集中到正确模块、减少重复分支；同样需要边界、生命周期和合法组合规则。

## 3. 示例一：只开始上传、停止读取

先问清“停止读取”指停止采集、停止发包还是两者都停。产品若把两者绑定，可以提供一对开始/停止操作；若允许断线继续采集，采集与传输需要分别表示，不能为了只用两个状态而误表达需求。

假设产品只允许一个客户端、一次活动采集，开始/停止在处理函数中有已验证的耗时上界：

| 当前状态 | 输入 | 行为与回复 | 后续状态 |
|---|---|---|---|
| IDLE | START | 尝试启动，实际成功才答成功 | RUNNING；失败则按观测保留/报告状态 |
| RUNNING | START，同参数 | 返回已经运行，不重复初始化 | RUNNING |
| RUNNING | START，不同参数 | 返回参数冲突；本阶段不支持运行中重配 | RUNNING |
| RUNNING | STOP | 停产并收回仍在使用的资源，实际完成才答成功 | IDLE |
| IDLE | STOP | 返回已经停止 | IDLE |
| 任意 | STATUS | 返回当前一致状态及必要诊断 | 不改变 |

这是逻辑接口示例，不是给真实设备发送的命令规范。两个状态足够的前提是启动/停止失败后仍能确认实际状态；若会部分执行且无法确认，需要显式记录该事实和处置，不能强行回 IDLE。

需要异步等待时，只对真实等待增加局部 STARTING 或 STOPPING，并保存截止点及必要关联信息。例如 STOPPING 时重复 STOP 合并为同一停止意图，START 返回 BUSY；停止完成才进入 IDLE，超时则返回明确失败/未确认并保留资源归属。具体重复命令响应可等待同一结果或返回当前进度，不必为每个重复请求新建状态。

如果这个功能只有立即完成的结果，不强制采用 ACCEPTED→RUNNING→多种终态的远程请求模型。确有异步长操作或结果丢失恢复需求，再引入必要的操作标识、进度与查询机制。简单路径仍需解释迟到响应是否可能混入下一次操作；可以采用关联标识或经证明的串行/会话隔离，不能仅以“单飞”为由忽略旧响应。

## 4. 示例二：产品逐步优化

| 迭代 | 局部增加什么 | 不必因此增加什么 |
|---|---|---|
| 上传改为分批 | 固定 buffer、长度、背压策略 | 系统级 BATCH_WAIT/SEND_1/SEND_2 模式 |
| 丢响应后允许查询 | 当前状态/最近操作结果及所需身份 | 任意深度历史、通用消息总线 |
| 停止等待 DMA/FPGA | 当前操作的停止阶段、deadline、资源交还 | 每个模块一个新 Task、完整事务引擎 |
| 增加运行中调参 | 候选配置和应用步骤；明确旧配置是否仍有效 | 不相干模块的状态重写 |
| 恢复偶发通信错误 | 一个重试 owner、有限计数、固定总截止点 | RETRY_1/RETRY_2/RETRY_3 全局状态 |
| 多个部件需协作重配 | 局部有序步骤及完成关联 | 还未需要的并行请求调度和持久去重 |

新增机制应让维护者看清：解决哪种失败、在哪个模块保留什么历史、哪些输入行为改变、失败后在哪里结束。扩展前做一份短影响清单：受影响的需求/命令与状态、数据解释、共享资源、旧版本行为和对应测试；简单修改可以用一段话完成。若不得不修改很多无关模块中的 `if (new_flag)`，先审视职责归属，不继续堆分支。

## 5. 示例三：多通道采集仪

按“独立生命周期”和“共享硬件约束”划分，不按通道数强制升级架构。

- 8 个通道同步启停，共享 ADC/FPGA 时序：一个采集状态机，加通道选择和参数；不需要 8 个状态机。
- 各通道能独立启停：复用一个通道状态结构/处理逻辑，以数组保存实例；不列举所有启用组合。
- 通道独立，但共用时钟、DMA 或 FPGA 配置：由共享资源的 owner 检查约束，协调受影响通道；数组和 bitmask 不能自动解决共享时钟冲突。
- 标定、采集和升级互斥：表达这一组能力/模式及入口条件；USB 是否连接仍由通信域管理。
- 多步协作反复出现相同超时/完成模板时，才考虑提取一个小的公共 transition helper；多个状态重复公共行为时才考虑 HSM。

多通道命令要选择整体接纳/完成或允许逐通道部分成功，并说明每个通道实际效果及共享资源状态。要求整体成功时，接纳前先检查共同约束；执行中仍可能部分失败，必须确认补偿结果或报告部分效果/未确认，不能假设全局回滚。重复 STOP 应针对原操作范围，不能误停止后来新开的通道。

局部状态可以增加，但普通业务调用方不应依赖 FPGA 内部每个等待步骤。对外提供稳定的操作与结果语义；诊断查询按需暴露阶段，避免上位机被迫复制固件内部状态机。

## 6. AI 的规模控制规则

先选择“当前最小足够方案”，不用给整个项目贴永久等级标签。一个复杂采集仪的新读状态字段仍可能只是局部修改；一个只有两条命令的协议也可能存在危险的无界等待。

新设计用行为示例代替虚构故障；问题排查才要求真实失败序列。简单任务只交付相关代码、短状态/命令表、必要失败处置和验证。不要求把所有参考表全部填完。

建议引入机制前说明三件事：当前缺口、最小实现、今后什么条件才值得升级。不得仅因未来“可能扩展”一次性加入多任务、消息总线、请求账本、四视图或 HSM。也不得为保持状态数字漂亮，把真实异步等待藏进 flag、回调或阻塞函数。

当用户删除某类需求时，一并考虑移除其专用状态和机制，避免只增不减。有实际重复、稳定接口或明确的可验证性收益时再提取公共代码；不设固定的重复次数门槛，也不为凑一个通用库而制造抽象。
